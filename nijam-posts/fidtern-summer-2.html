My second summer at Fidelity Investments as a Software Engineer intern began with the illusion of familiarity: the same badge with the awkward headshot, the same parking habits, the same lunch orders and anticipation for curly fries, the same complimentary sun chips. However, my experience and learnings this summer were immensely different from last year. This summer I was a Software Engineer intern for Fidelity's Workplace Investing's Single-Sign-On team. Uniquely, our team consists of half developers and half analysts, giving me a first-hand insight into both the techonology and the user experiences, client conversations, and the business of the product. Moreover, this opportunity to work in the security space at a pivotal time in technology with Claude Mythos and other powerful LLMs and the security vulnerabilities they present, gave me a seat in conversations that helped me understand the company's priorities and the thought processes in each and every decision made regaridng these emrging technolgoies.

My Summer Fidtern Project

Alongside my co-intern Nicholas Houghton, I built a feature in a product called SSO Admin, the interface in which our analysts and other business users manage the Single-Sign-On experience for Fidelity's clients. Our feature, called "SSO Admin User Management," allows analysts to manage the users of SSO Admin, including adding and removing users, assigning roles, and managing permissions. This feature was built with security in mind, as it allows analysts to manage access to sensitive information and functionality within SSO Admin. will add, edit, and maintain SSO connections. For example, if Company XYZ wanted to add Health Insurance ABC as a new SSO connection, the analyst would use this application to add the connection and assign the appropriate permissions to the users who need access to it. This feature was built with security in mind, as it allows analysts to manage access to sensitive information and functionality within SSO Admin. While analysts primarily work with Client IDs to configure these connections, the dashboards on this app do no show client names at all. After review and due to plans of expanding this tool's access to other teams and new members, we realized the criticality of adding names alongside the ids for quick verification. Moreover, we added a search functionality when an analysts wants to search a preexisting connection to add a client. This search feature also provides clear error handling and provides feedback to the users when ids that already exist or are invalid are entered. Using Angular and TypeScript for the frontend, REST clients, JAva, and Spring Boot for the backend, we built this feature from scratch and deployed it to production. Additional tools we used included Bruno to test the API, Jira for project management and story-tracking, GitHub copilot for both secure development and testing increasing our efficiency, and Git/Github for PRs and CI/CD.
